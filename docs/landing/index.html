What GRiD supports

Joints and algorithms.

Joint types

  • Revolute and continuous, prismatic, fixed
  • Floating base (free-flyer) and fixed base
  • Mimic joints, including chained mimics
  • Arbitrary (skew) joint axes
  • Helical, planar, and translation joints
  • Spherical (ball) joints
  • Optional joint damping and friction

Algorithms

  • Inverse dynamics (RNEA), forward dynamics (ABA and via the mass-matrix inverse), mass matrix (CRBA)
  • Analytical gradients and Hessians of inverse and forward dynamics
  • End-effector pose, Jacobian, and Hessian; frame Jacobians in local, world, or local-world-aligned coordinates
  • Centroidal momentum matrix and its derivatives; Coriolis matrix; gravity and bias terms
  • External forces and their gradients; inertial-parameter regressors and parameter gradients
  • Time integrators with gradients, Euler and semi-implicit Euler step Hessians, and a trajectory-optimization plant layer
  • Two-tier collision checking on spherized geometry

Joint support is operation-specific. Mimic and spherical models use a dense CRBA-based Minv path; spherical joints do not support multi-stage integrator gradients. Step Hessians are a NumPy/CUDA surface, not a JAX or PyTorch handle method. See support and restrictions and the library overview.

From model to computation

Your robot model becomes reusable GPU code.

Collision routines use the generated CUDA interface and require complete geometry coverage. Analytical Hessians are explicit outputs, not nested higher-order autograd; see differentiation support.

Benchmark Results

One collection on an RTX 5090 covers iiwa14, go2, and G1 at batch sizes 16 through 1024 and fifteen operations, with supported comparisons against Pinocchio, MJX, MuJoCo Warp, MuJoCo CPU, BARD, and Frax. GRiD's CUDA compute-only calls outperform the GPU libraries' resident calls on most matched cells; larger batches also expose gains over CPU baselines after host–device transfers. The result depends on the operation and API boundary. Timed cells were checked against an fp64 reference before and after timing; retained accuracy warnings and timing variability are marked. Get started

Start with one robot and one computation.

This preview uses the current development branch. From a machine with a compatible NVIDIA GPU, CUDA toolkit, and C++ compiler:

git clone --recursive --branch modernizing-tests https://github.com/A2R-Lab/GRiD.git
cd GRiD
bash install/base_install.sh
source .venv/bin/activate

Run this from the repository root. Building only the operation you need keeps the first example focused.

import numpy as np
import grid_rbd

robot = grid_rbd.load_robot(
    "config/robot_assets/iiwa14.urdf",
    algorithm_list=["forward_dynamics"],
    enable_mujoco_kernels=False,
)
q = np.zeros((8, robot.nq), dtype=np.float32)
qd, tau = (np.zeros((8, robot.nv), dtype=np.float32) for _ in range(2))
qdd = robot.forward_dynamics(q, qd, tau)
print(qdd.shape)  # (8, 7)
robot.close()

The first load generates and compiles code; it can take minutes. Later loads reuse compatible cached artifacts. This NumPy example moves inputs and outputs through host memory. JAX and PyTorch require separately installed CUDA-enabled frameworks.

Platform and interface scope

Current validation targets Linux x86_64 with NVIDIA CUDA. Generated code can be rebuilt for different GPU architectures; compiled robot binaries are architecture-specific. Jetson is a target, not a deployment certified by the current receipt. Source-checkout installation is supported; published wheels are not available.

Joint types, operation coverage, runtime contexts, differentiation, and graph-capture restrictions are documented in compatibility and known limitations. New release measurements and a fresh full validation receipt remain release gates.
